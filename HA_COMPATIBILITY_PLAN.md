# Plan: Marketplace readiness without dropping older Home Assistant support

Prepared November 4, 2026. Implemented locally on the same date. The status below records local validation before PR submission; no integration release has been published.

## Implementation status

- The minimum-version imports and options reload path are fixed. HA 2025.2.0 remains the declared minimum.
- Finished English translations replace `strings.json`; hassfest passes with zero invalid integrations.
- Exact-version CI exports locked test dependencies, resolves each HA target separately, checks dependency consistency and the installed HA version, and runs daily/manual/PR tests.
- All **45 tests pass on each of HA 2025.2.0, 2026.10.4, and 2026.11.0**, using the locked test dependency versions. Lint and formatting pass. Local `uv sync --locked` / `uv run pytest` also pass.
- README installation and development instructions cover both HACS and Marketplace.
- A disposable two-process upgrade from HA 2026.10.4 to 2026.11.0 retained fixed/home-tracking entries, device/entity IDs, a custom name, and a template reference. Seeded legacy HACS storage was adopted by the real Marketplace, preserving the repository's update entity ID/name.
- Marketplace's actual installer downloaded the already published `v2.2.1-beta.1` into that disposable copy, validated its manifest and created a restart repair. A subsequent new HA process loaded that downloaded version and retained IDs, names and working forecasts. This exercises the public download/install path, not the unpublished local fixes.
- Remaining boundary: legacy HACS storage was seeded, not generated by a signed-in HACS account. No household configuration was touched. A full account-backed rehearsal and publishing the local fixes remain release work.

The implementation sequence below records the agreed scope.

## Decision

Keep **Home Assistant 2025.2.0** as the target minimum and make it a tested promise. Do not raise the minimum to 2026.11 just because Marketplace is built in there. First restore the existing advertised baseline; consider an earlier minimum only if tests and the API audit support it without additional compatibility machinery.

The previous assessment tested the current HA runtime, not the advertised minimum. Follow-up source checks found two real baseline incompatibilities: the unconditional imports of `OptionsFlowWithReload` and `AddConfigEntryEntitiesCallback` do not exist in HA 2025.2.0. This does not invalidate the successful 2026.11 checks, but it means the current `hacs.json` minimum is not reliable today.

These are integration versions, **not Home Assistant Core versions**. The public dataset groups by the `meteoam` domain, so it may include the original integration or other forks using that domain; it does not identify users of this specific repository. Analytics is opt-in and counts installations, not people.

The current public datasets expose global HA version totals and per-custom-integration release totals separately. They do not expose the HA-version distribution conditional on using MeteoAM, nor per-installation records that would allow a join. Global HA adoption and MeteoAM release adoption cannot establish what HA versions this integration's users run. There is therefore no user-specific evidence here to justify dropping older HA versions.

## Implementation sequence

### 1. Establish and restore the minimum (gap 2 prerequisite)

Files: `custom_components/meteoam/config_flow.py`, `weather.py`, tests; inspect the remaining integration imports before editing.

- Reproduce config-flow and weather imports on HA 2025.2.0 / Python 3.13.
- Replace the newer entity callback annotation/import with an API available across the supported range.
- Use the common `OptionsFlow` API with a supported explicit reload path if that is sufficient across the range. Prefer one shared implementation over version checks or separate implementations. Preserve the existing options-data replacement behavior.
- Verify successful options edits take effect exactly once and canceling the form changes nothing. Do not combine automatic reload with an update listener, which newer HA rejects.
- Check the other imports and setup/forecast/unload paths on the same baseline. Keep unique IDs and config-entry version unchanged unless a separately demonstrated defect requires a migration.

Acceptance: import, setup, current weather, daily/hourly forecasts, options editing, reload, unload, and track-home behavior pass on the minimum and current HA. Coordinates that have not changed retain their IDs. If the baseline needs substantial compatibility code, record the concrete blocker and smallest viable minimum before deciding on a higher floor.

### 2. Package finished translations (gap 1)

Files: `custom_components/meteoam/translations/en.json`, translation tests, existing `strings.json` as appropriate.

- Add a complete English translation file containing literal strings, resolving all existing `[%key:...%]` references.
- Cover config forms, options, duplicate/no-home messages and the `update_failed` exception. Use one canonical text source; do not add a translation generator.
- Verify HA returns nonempty translation keys on both ends of the supported range, and that placeholders match the exceptions.
- Run hassfest. Treat this as packaging/UI repair, not a config-entry migration.

Acceptance: forms have their intended labels, translated error messages resolve, and no unresolved reference tokens are shipped in the runtime English translation file.

### 3. Make CI test the promised versions (gap 2)

Files: `.github/workflows/test.yml`, `pyproject.toml`, `uv.lock`, focused lifecycle/translation tests; adjust `.python-version` only if necessary for the chosen local default.

Required blocking jobs:
- **Minimum:** HA 2025.2.0, Python 3.13.
- **Last HACS-only monthly release:** HA 2026.10.4, Python 3.14.
- **Marketplace release:** HA 2026.11.0, Python 3.14 (>=3.14.2).

- Pin each HA target explicitly and print/assert its installed version before testing. Separate the application support floor from the Python used by each test job.
- Existing tests do not use the HA test plugin fixtures. Use explicit `pytest-asyncio` for those tests and a small shared real-HA lifecycle fixture/check, avoiding the currently incompatible test plugin if it is unnecessary. Do not silently override its dependency pin and leave an inconsistent environment in CI.
- Resolve any per-target dependency differences explicitly in CI; never let a shared lockfile silently downgrade the target HA release. Keep normal dependency resolution reproducible and check the lockfile changes.
- Move the useful assertions from the temporary 2026.11 smoke script into maintained tests, with HA APIs verified against the minimum. Mock only external weather responses; use real loader, config entries, weather services and registries.
- Add a scheduled/manual run so compatibility checks are not limited to PRs. Keep HACS validation and hassfest.
- A separate beta job can be nonblocking when an actual newer beta exists; test its installed version explicitly. Do not make old-version support depend on beta tooling availability.

Acceptance: all blocking jobs pass with the exact versions declared, including lifecycle and translation checks. New-HA coverage must not replace minimum-version coverage.

### 4. Document both installation paths (gap 3)

Files: `README.md`, `hacs.json` and dependency metadata only if the verified minimum needs correction.

- HA 2026.11+: install from Settings > Marketplace; first config-flow installation can open setup immediately; updates of a loaded integration still need a restart.
- Older supported HA: retain HACS instructions. Keep manual installation instructions.
- Explain automatic HACS migration: keep MeteoAM configured, preserve its files and entries, and do not uninstall/re-add it for the transition.
- Document the tested minimum and distinguish user HA requirements from contributor/test Python requirements. Keep `hacs.json`, README and dependency metadata consistent with evidence.

Acceptance: a user on either side of the Marketplace transition can follow the right instructions without unnecessarily recreating entities.

### 5. Verify the actual transition before a compatibility announcement

- Use a disposable older HA + HACS configuration with MeteoAM installed, including fixed and home-tracking locations, a renamed entity and a simple dashboard/automation reference.
- Record its config-entry, device and entity IDs, upgrade to 2026.11, and check the repository is still managed in Marketplace, IDs and references survive, and weather/forecasts work.
- Exercise one Marketplace integration update and the requested restart. Keep rollback to a disposable backup available.
- Release the small fixes as a prerelease first, with clear tested-version claims; no new data migration unless tests establish a need.

Acceptance: migration and update rehearsal pass. A reload on a fresh 2026.11 installation alone is insufficient evidence of this transition.

## Scope and completion

This plan repairs the current minimum-version promise and the three identified gaps. It does not add analytics, telemetry, abstraction layers, extra configuration, mandatory manifest categories, branding changes or unrelated cleanup.

Done means: exact-version CI is green, translations resolve, both installation paths are documented, and a real HACS-to-Marketplace migration has been rehearsed. Compatibility below 2025.2 remains unclaimed until separately verified. Public adoption data cannot remove that uncertainty.
